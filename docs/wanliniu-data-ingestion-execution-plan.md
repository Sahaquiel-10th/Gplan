# 万里牛数据接入与甲方 API 执行规划

> 文档状态：第一期执行基线
> 更新日期：2026-08-19
> 适用范围：万里牛 ERP → 阿里云 RDS `gplan_data` → 小象 G 计划服务端 → 甲方 API

## 1. 已确认的总体方案

甲方 API 从小象 G 计划服务器提供，不直接访问万里牛，也不直接连接 RDS。

```text
万里牛 ERP
  ↓ 定时同步、分页、重试、增量游标
RDS ODS 原始镜像表
  ↓ 清洗、映射、统一业务口径
内部业务视图/汇总表
  ↓ 固定字段和数据含义
API 契约视图 api_*_v1
  ↓ 服务端鉴权、分页、限流、审计
甲方 HTTP API /api/v1/data/*
```

核心原则：

- 万里牛是第一期数据源，但不是甲方 API 的组成部分。
- ODS 表保留万里牛原始业务粒度，不为甲方口径覆盖或丢弃源数据。
- 合并店铺、合并仓库、产品别名等规则放在映射与业务口径层。
- 甲方只能依赖固定的 v1 API 契约；内部可以换表、换视图、换同步方式、增加数据源。
- v1 发布后不删除字段、不改字段类型、不改变已有字段含义；破坏性变化另发 v2，并继续保留 v1。

## 2. 第一期交付范围

### 2.1 出货维度

甲方第一期需要：

| 甲方字段 | 内部来源 | 说明 |
| --- | --- | --- |
| `shipment_time` | 销售出库单 `bill_date` | 出货时间，统一为北京时间 |
| `store_code` | 报表主体映射 | 稳定编码，不直接使用万里牛店铺名称作为主键 |
| `store_name` | 报表主体映射 | 甲方口径店铺名称，可由多个源店铺合并 |
| `product_code` | 出库明细 `sku_no` | 第一期按 SKU 编码 |
| `product_name` | 出库明细/商品主数据 | 优先使用商品名称，缺失时回退规格名称 |
| `quantity` | 出库明细 `nums` | 出货数量 |
| `gmv` | 明细实付或销售金额 | 口径须在上线前确认 |

万里牛接口：`POST /erp/sale/stock/out/query`

### 2.2 库存维度

甲方第一期需要：

| 甲方字段 | 内部来源 | 说明 |
| --- | --- | --- |
| `store_code` | 报表主体映射 | 甲方业务主体，不等同于源仓库 |
| `store_name` | 报表主体映射 | 可以合并一个或多个仓库 |
| `product_code` | 分仓库存 `sku_code` | 第一期按 SKU 编码 |
| `product_name` | 商品主数据 | 库存接口缺少完整商品名时关联补全 |
| `inventory_quantity` | 分仓库存 `quantity` | 实际库存；不能与可售库存混用 |
| `available_quantity` | `quantity - lock_size` | 扩展字段，便于后续问数 |
| `snapshot_time` | 同步批次时间 | 表示这批库存数据截至何时 |

万里牛接口：`POST /erp/open/inventory/items/get/by/modifytimev2`

注意：万里牛库存是“仓库 + SKU”粒度，不是店铺库存。多个店铺共用同一个仓库时，该仓库只能计算一次；多个独立仓库归属同一报表主体时，才按规则汇总。

### 2.3 入库维度

甲方第一期需要：

| 甲方字段 | 内部来源 | 说明 |
| --- | --- | --- |
| `inbound_time` | 采购入库单 `bill_date` | 入库时间，统一为北京时间 |
| `product_code` | 入库明细 `spec_code` | 第一期按 SKU 编码 |
| `product_name` | 入库明细/商品主数据 | 商品名称 |
| `inbound_quantity` | 入库明细 `nums` | 入库数量 |

万里牛接口：`POST /erp/purchase/purchasebill/stockin/query`

第一期暂把“入库”定义为采购入库。销售退货入库、调拨入库、生产入库及其他入库不默认混入，待甲方确认后扩展。

### 2.4 商品主数据

商品主数据用于统一商品编码、商品名称和规格信息，并补全库存记录中的名称。

万里牛接口：`POST /erp/goods/spec/open/query/goodswithspeclist`

- [x] `ods_wln_purchase_inbound_items`：采购入库明细。

第一版建表草案：[`deploy/gplan-data-phase1-schema.sql`](../deploy/gplan-data-phase1-schema.sql)

### 3.3 业务映射表

建表时补充以下中立对象，不在名称中绑定万里牛：

- [ ] `dim_reporting_entities`
  - 定义甲方可见的稳定业务主体，如“小象优选”。
  - 至少包含 `entity_code`、`entity_name`、`entity_type`、`enabled`。
- [ ] `map_source_reporting_entities`
  - 把源店铺、源仓库映射到甲方业务主体。
  - 至少包含 `source_system`、`source_type`、`source_code`、`entity_code`、生效起止时间、是否启用。
  - `source_type` 第一期支持 `SHOP`、`STORAGE`，以后可增加公司、渠道等类型。
- [ ] `map_product_aliases`（可在出现真实需求时启用）
  - 处理多个源 SKU 对应同一甲方商品，或甲方自定义商品名称。

映射规则不得直接硬编码在 API 路由里。调整店铺/仓库归属时，只修改映射数据或内部业务视图。

### 3.4 内部业务视图

- [x] `vw_wln_shipments_v1`：万里牛出货明细内部视图。
- [x] `vw_wln_inventory_v1`：万里牛分仓库存内部视图。
- [x] `vw_wln_inbound_v1`：万里牛采购入库内部视图。

这些视图属于内部实现，可以修改或替换，不能作为甲方长期契约。

### 3.5 稳定 API 契约视图

- [ ] `api_shipments_v1`
- [ ] `api_inventory_v1`
- [ ] `api_inbounds_v1`

要求：

- 名称和字段不出现 `wln`、`wanliniu` 等源系统标识。
- 明确列出字段，不使用 `SELECT *`。
- 字段名称、类型、单位、时区、空值处理和业务含义形成契约。
- 内部表替换时使用 `CREATE OR REPLACE VIEW` 切换来源，保持契约不变。
- 如果聚合查询量增长，可把底层改成汇总表，API 契约视图仍保持不变。

### 3.6 库存历史快照（建议第一期同时做）

- [ ] `fact_inventory_snapshots`
  - 保存每日或每次关键同步后的库存快照。
  - 支持“昨天库存多少”“某次活动前后库存变化”等历史问题。

`ods_wln_inventory_current` 只保存当前值，无法单独回答过去某一时点的库存。快照表可以晚于首批同步上线，但应在正式积累经营数据前启用。

## 4. 同步程序规划

### 4.1 同步任务拆分

- [x] `sync-wln-shops`
- [x] `sync-wln-products`
- [x] `sync-wln-sale-outbound`
- [x] `sync-wln-inventory`
- [x] `sync-wln-purchase-inbound`

每个任务必须独立分页、重试和记录游标，不能因为一个对象失败而阻断其他对象。

### 4.2 统一同步规则

- [x] 凭证仅保存在 ECS 服务端环境变量或密钥服务，不进入前端、数据库普通字段和 Git。
- [x] 所有请求使用万里牛官方签名方式和官方接口路径。
- [x] 每次执行先写入 `data_sync_runs`，结束后记录成功/失败、读取数、写入数和错误摘要。
- [x] 增量游标在全部分页成功后才前移；任何一页失败都不提交新游标。
- [x] 增量时间窗保留安全重叠区间，通过唯一键 Upsert 去重，避免边界数据遗漏。
- [x] 单据头和明细在同一数据库事务中落库，避免只有单头或只有明细。
- [x] 保留脱敏后的 `raw_payload`、`sync_run_id`、`ingested_at`，便于追溯和重算。
- [x] API 限流、超时、网络失败采用有限次数的指数退避重试。
- [x] 日志不得输出 App Secret、签名原文或完整客户敏感数据。

### 4.3 建议同步频率

| 对象 | 首次同步 | 增量同步 | 补偿/核对 |
| --- | --- | --- | --- |
| 店铺 | 全量 | 每 6 小时 | 每日全量核对 |
| 商品/SKU | 全量分页 | 每 1-6 小时 | 每日全量核对 |
| 销售出库 | 先取接口允许范围内的历史 | 每 10-15 分钟 | 每日重拉最近 3 天 |
| 当前库存 | 全量分页 | 每 15-30 分钟 | 每日全量核对 |
| 采购入库 | 先取接口允许范围内的历史 | 每 30-60 分钟 | 每日重拉最近 3 天 |
| 库存快照 | 首次全量库存后生成 | 每日固定时点 | 失败后当天补跑 |

接口约束需落实到程序：

- 分仓库存增量查询的开始/结束时间差最大 7 天，分页大小最大 200。
- 销售出库和采购入库的修改时间查询受近 3 个月限制；更早历史需要与万里牛确认可用接口或采用数据导出回灌。

### 4.4 调度方式

第一期沿用当前 Node.js、ECS、PM2 技术栈：

- [ ] 同步程序作为独立 worker 进程运行，不挂在用户请求线程里。
- [ ] 由 PM2 或服务器定时任务触发；同一任务增加分布式锁/数据库锁，禁止重复并发。
- [x] 管理后台的“立即同步”只负责触发任务并展示结果，不直接在浏览器请求中拉完整数据。
- [ ] 正式运行后增加失败告警和最近成功时间展示。

## 5. 甲方 API 规划

### 5.1 服务端路径

- [ ] `GET /api/v1/data/shipments`
- [ ] `GET /api/v1/data/inventory`
- [ ] `GET /api/v1/data/inbounds`

路径不包含万里牛名称，以便未来增加其他 ERP、店铺或仓储数据源。

### 5.2 通用能力

- [ ] HTTPS。
- [ ] 独立甲方 API Token，不复用数据库账号和万里牛凭证。
- [ ] Token 权限范围按接口划分，例如 `data:shipments:read`。
- [ ] 必填/选填查询参数校验。
- [ ] 分页、最大时间区间和最大页大小限制。
- [ ] 统一错误结构和请求 ID。
- [ ] 限流、访问日志和审计日志。
- [ ] 返回 `data_updated_at`，让甲方知道数据新鲜度。
- [ ] API 只查询 `api_*_v1` 契约视图，不直接读取 ODS 表。

### 5.3 v1 契约冻结规则

允许内部无感调整：

- 换表、拆表、增加索引。
- 视图切换到汇总表。
- 多店/多仓合并和归属调整。
- 商品名称和别名映射。
- 增加新的源平台。
- 修复同步和清洗逻辑。

不得直接修改 v1：

- 删除或重命名已有字段。
- 改变字段类型、单位或时区。
- 把 SKU 粒度改成 SPU 粒度。
- 把实际库存改成可售库存但仍使用原字段名。
- 改变 GMV、入库范围等已有业务定义。

确需破坏性改变时，新建 `/api/v2/data/*`，并保持 v1 继续可用。

## 7. 上线前必须确认的业务口径

以下事项不阻塞建 ODS 表，但会阻塞甲方 v1 契约冻结：

1. `gmv`：优先使用明细分摊实付 `actual_pay`，还是使用明细销售金额 `sum_sale`。
2. `inventory_quantity`：甲方要实际库存 `quantity`，还是可售库存 `quantity - lock_size`。
3. “一个店”的含义：报表主体、销售店铺、经营组织还是库存归属主体。
4. 店铺和仓库的映射清单，以及共用仓库的去重规则。
5. “入库”是否只含采购入库，是否包含销售退货、调拨、生产及其他入库。
6. 商品粒度使用 SKU 还是 SPU；当前方案按 SKU。
7. 数据时区为 `Asia/Shanghai`，金额默认人民币，数量是否允许小数。
8. 甲方需要的历史起始日期、更新频率和最长可接受延迟。

## 8. 故障、切换与回退原则

- 新表先建、历史先回填、对账通过后再切换契约视图，不在旧表上做高风险直接改造。
- `api_*_v1` 切换底层前保留旧查询定义和回退 SQL。
- 同步异常时继续提供最近一次成功数据，并在响应中返回 `data_updated_at`；超过 SLA 后告警。
- 源接口故障不允许把现有库存或历史流水清空。
- 删除、重建、大批量覆盖前先做备份或使用影子表。
- 甲方 v1 一旦发布，回退内部实现不能改变对外字段与业务含义。
