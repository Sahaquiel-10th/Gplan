# 企业大脑演进路线图

## 1. 文档目的

本文是在《AI 问数平台数据接入方案》基础上形成的总体阶段计划，回答三个问题：

1. 平台从现在开始应按几层建设。
2. 每一层分别解决什么问题，边界在哪里。
3. 如何分阶段把当前企业 AI 工作台演进为可持续使用的“企业大脑”。

这里所说的企业大脑，不是一个无所不能的大模型，而是一套能够持续完成以下闭环的企业智能系统：

```text
感知企业状态
→ 记住资料、规则和历史
→ 理解指标与业务关系
→ 分析问题并提出建议
→ 在授权范围内推动行动
→ 跟踪行动结果并形成反馈
```

## 2. 总体结论：7 层架构 + 1 套横向治理体系

原《AI 问数平台数据接入方案》的正文实际包含 5 层：数据源、数据接入、业务数据库、指标语义、AI 问数。为了覆盖当前已经存在的企业知识库、智能体平台，以及未来的驾驶舱、预警和行动闭环，企业大脑建议统一为 7 层。

```text
第 7 层  应用与决策层
         对话问数、经营驾驶舱、日报、预警、任务与复盘

第 6 层  智能体与编排层
         意图识别、工具选择、分析流程、多智能体协同、结果生成

第 5 层  企业知识与记忆层
         企业资料、业务经验、制度、方法论、个人记忆、分析模板

第 4 层  指标语义与数据工具层
         指标口径、维度、权限、查询工具、对比工具、预测工具

第 3 层  数据存储与建模层
         原始数据、统一明细、维度主数据、汇总数据、数据质量

第 2 层  数据接入与同步层
         API、签名、分页、增量、重试、调度、水位、同步留痕

第 1 层  企业数据源层
         ERP、线上店铺、银行、支付、广告、会员、客服、财务系统
```

横向贯穿所有层的是一套治理体系：

```text
身份与权限 + 数据分级 + 脱敏 + 审计 + 指标治理
+ 数据质量 + 成本控制 + 可观测性 + 人工审批 + 安全边界
```

治理不是第 8 层，因为它不能只在某个位置生效，而必须贯穿数据进入、存储、查询、模型分析和结果展示的全过程。

## 3. 七层分别做什么

### 第 1 层：企业数据源层

目标：明确企业真实数据分别产生在哪里，确定各类事实的权威来源。

首批数据源：

- 万里牛 ERP：商品、SKU、店铺、仓库、库存、销售出库、售后、采购等。
- 淘宝/天猫、拼多多等店铺平台：平台订单、活动、优惠、流量、广告、平台退款和结算。
- 银行和企业支付宝：账户余额、资金流水、对账单、回单、渠道账务。
- 企业知识库：制度、商品资料、经营经验、活动复盘、业务方法论。

这一层的重要原则：

- 不假设一个系统可以提供全部事实。
- 每个核心业务事实必须指定权威来源。
- 同一个事实来自多个系统时，要定义核对关系，而不是直接覆盖。

典型事实链路：

```text
平台下单 → ERP 发货/出库 → 平台结算 → 银行到账
```

### 第 2 层：数据接入与同步层

目标：将外部系统不稳定、各不相同的接口，转换为平台内部稳定、可追踪的数据流。

职责：

- 凭证和证书管理。
- 接口签名、鉴权和环境切换。
- 全量初始化与增量同步。
- 分页、限流、超时、重试和断点续传。
- 同步水位和时间窗口管理。
- 幂等写入、重复数据处理。
- 同步任务、错误样本和调用量留痕。
- 必要时提供少量受控实时查询。

这一层只负责“可靠搬运和记录”，不定义销售额等经营口径。

### 第 3 层：数据存储与建模层

目标：形成平台自己的经营数据底座，使数据可追溯、可统一、可重算。

建议内部再分三类模型，但对外仍算同一个架构层：

1. ODS 原始层：尽量完整保留来源数据和原始报文。
2. DWD 统一明细层：统一店铺、SKU、仓库、订单、出库、退款、资金流水等业务实体。
3. DWS/DM 汇总层：形成店铺日、商品日、库存日、现金流日等高频查询模型。

第一阶段可以继续使用 MySQL，但经营数据必须与当前保存聊天状态的 `app_state` JSON 分开。可以使用同一个 RDS 实例，建立独立数据库、账号和连接池。

建议第一批模型：

```text
同步控制：
data_sync_job
data_sync_cursor
data_sync_error

原始层：
ods_wln_shop
ods_wln_warehouse
ods_wln_product
ods_wln_inventory
ods_wln_sales_outbound
ods_wln_after_sale

统一层：
dim_store
dim_product_sku
dim_warehouse
fct_sales
fct_refund
fct_inventory_snapshot

汇总层：
dws_store_day
dws_product_day
dws_inventory_day
```

所有原始表应统一保留来源主键、来源更新时间、接入时间、同步批次和原始报文，保证后续可以追溯和重算。

原始报文并不代表无条件保存全部字段。与经营分析无关的联系人、手机号、地址等个人信息应在接入时删除或脱敏；只有经过确认的必要字段才能进入经营数据库。

### 第 4 层：指标语义与数据工具层

目标：把“数据库字段”转换成全公司统一理解的“业务指标和查询能力”。

每个指标必须明确：

- 中文名称和业务解释。
- 计算公式。
- 权威数据来源。
- 时间口径。
- 可用维度。
- 包含和排除范围。
- 数据延迟。
- 权限要求。
- 负责人和版本。

例如“销售额”不能只写一个 SQL，需要明确它究竟是：

- 平台下单金额；
- 买家实付金额；
- ERP 销售出库金额；
- 平台结算金额；
- 财务确认收入。

AI 不直接访问原始表，也不自由生成生产 SQL。AI 只能调用经过登记、校验和授权的数据工具，例如：

```text
get_store_daily_summary
get_store_trend
get_product_sales_rank
get_inventory_snapshot
get_inventory_warning
get_promotion_effect
get_cash_daily_summary
get_store_cash_reconciliation
```

### 第 5 层：企业知识与记忆层

目标：让数据分析不仅有数字，还有企业自己的产品资料、规则、经验和历史背景。

包含：

- 企业知识库：制度、SOP、产品资料、营销经验、历史复盘。
- 用户显式记忆：用户要求长期记住的偏好和事实。
- 受控隐式记忆：从历史互动中沉淀的稳定偏好。
- 分析模板：经营日报、大促复盘、库存分析等标准框架。
- 决策记录：当时为什么做某个决策，使用了哪些数据和假设。

这一层与指标语义层并列：

- 指标语义层回答“发生了什么、变化多大”。
- 知识与记忆层帮助回答“为什么、按公司经验应该怎么办”。

知识库内容不能覆盖结构化数据事实。两者冲突时，数字结论以经过治理的数据工具为准，同时提示知识资料可能过期。

### 第 6 层：智能体与编排层

目标：把用户问题转换为受控的分析流程，而不是只进行一次普通聊天。

标准执行链：

```text
理解问题
→ 识别时间、对象和任务
→ 判断是否需要补问
→ 选择数据工具和知识检索
→ 权限校验
→ 获取结构化结果
→ 执行对比、归因和风险检查
→ 生成结论、证据和建议
→ 保存本次分析记录
```

第一版可以采用两段式编排，降低对模型供应商 Function Calling 能力的依赖：

```text
模型生成受约束的查询意图 JSON
→ 后端验证并执行工具
→ 模型读取结果后生成最终回答
```

不同智能体共享同一个数据工具底座，但拥有不同的分析流程和权限。例如：

- 店铺经营分析智能体。
- 商品上新建议智能体。
- 活动策划与复盘智能体。
- 库存预警智能体。
- 现金流日报智能体。
- 管理层经营分析智能体。

### 第 7 层：应用与决策层

目标：让企业员工和管理层真正用起来，并让分析进入日常经营流程。

应用形态：

- 对话问数：员工自然语言提问。
- 经营驾驶舱：管理层查看稳定指标和趋势。
- 自动日报/周报：按固定模板生成并推送。
- 主动预警：发现异常后通知责任人。
- 决策建议：展示结论、证据、风险和推荐动作。
- 任务与复盘：记录是否采纳建议、谁负责、结果如何。

驾驶舱与对话不是两套数据系统。两者必须调用同一套指标定义和权限体系，避免出现“图表一个数、AI 又说另一个数”。

## 4. 企业大脑的四条能力主线

七层架构要同时服务四条主线：

### 4.1 企业记忆

把资料、经验、决策记录和历史结果组织成可检索、可更新、可授权的企业记忆。

### 4.2 经营感知

持续接入业务和资金数据，知道企业当前发生了什么，并能识别数据延迟和异常。

### 4.3 分析决策

使用统一指标、知识和分析模板，解释变化、评估方案、给出建议，并展示证据和不确定性。

### 4.4 行动反馈

把建议转成待办、审批、预警或业务动作，跟踪是否执行以及执行效果，让结果回流成为下一次决策的依据。

只有前三条时，平台是“懂企业的分析助手”；四条全部形成闭环后，才接近真正的企业大脑。

## 5. 阶段路线图

阶段编号表示能力成熟度，不强行绑定固定月份。每一阶段必须通过验收后再扩大数据源和智能体范围。

### 阶段 0：统一口径与工程地基

阶段目标：把已有思路变成可以持续建设的工程边界。

主要工作：

- 确认七层架构和负责人。
- 建立独立经营数据库，不使用 `app_state` JSON 存经营数据。
- 建立数据库迁移机制、环境配置和密钥管理方式。
- 建立连接器、同步任务、指标工具的代码目录和接口规范。
- 建立基础权限、操作审计和数据查询审计。
- 确认第一批核心指标口径，尤其是销售额、订单数、退款和库存。
- 修正万里牛接口清单及凭证规则。

阶段产物：

- 数据库设计稿和迁移脚本。
- 数据源登记表。
- 指标字典 V1。
- 权限矩阵 V1。
- 同步任务规范。
- 数据质量核对清单。

验收标准：

- 团队能明确回答每一个核心指标来自哪里、如何计算、谁能查看。
- 测试、生产凭证隔离，密钥不出现在前端和模型上下文中。
- 新连接器可以按统一规范接入，而不是继续堆在单个后端文件里。

### 阶段 1：万里牛经营数据闭环

阶段目标：让平台第一次拥有可信、可重复查询的真实经营数据。

接入范围：

- 店铺。
- 仓库。
- 商品和 SKU。
- 分仓库存。
- 销售出库单。
- 系统售后单。

主要工作：

- 实现万里牛签名、分页、重试和增量水位。
- 完成全量初始化和定时增量同步。
- 落地 ODS、统一明细和日汇总表。
- 完成三项数据工具：店铺经营概览、商品销售排行、库存快照。
- 建立同步监控、错误重跑和人工补数入口。

阶段产物：

- 万里牛真实连接器。
- 第一批经营事实表和汇总表。
- 数据接入管理页真实状态。
- 数据核对报告。

验收标准：

- 重复执行同一同步任务不会制造重复数据。
- 同步中断后可以从正确水位继续。
- 连续至少 3 个营业日的出库、售后和库存能与万里牛后台核对。
- 所有结果显示数据更新时间和统计口径。
- 当前阶段不把万里牛“订单查询”误当成淘系、拼多多全部订单来源。

阶段结束时，平台从“有知识的 AI 工作台”升级为“有企业经营数据的 AI 工作台”。

### 阶段 2：可信问数与经营分析智能体

阶段目标：让员工可以自然语言查询数据，并获得有证据的经营分析。

主要工作：

- 建立查询意图结构和后端工具路由。
- 实现工具级权限校验、参数校验、查询超时和结果大小限制。
- 建立指标工具调用日志。
- 将结构化数据结果与企业知识库共同交给模型分析。
- 首批上线店铺经营分析、商品销售分析、库存分析智能体。
- 回答中展示统计区间、数据新鲜度、指标口径和异常说明。

首批问题：

- 昨天销售情况如何？
- 哪些商品销售增长或下降最明显？
- 当前哪些 SKU 存在缺货或积压风险？
- 某个商品适合与哪些现有商品组合上架？

验收标准：

- AI 不直接访问原始表和密钥。
- 同一个指标在对话和后台查询中的数值一致。
- 越权用户无法通过提示词获得数据。
- 对缺少数据的问题明确说明缺口，不编造答案。
- 典型问题形成稳定测试集，核心指标查询正确率达到上线要求。

阶段结束时，平台升级为“可信的企业问数与经营分析助手”。

### 阶段 3：店铺平台直连与活动决策

阶段目标：补齐 ERP 无法提供的线上平台事实，支持活动策划、上新建议和活动复盘。

接入范围按业务优先级逐个平台推进：

- 淘宝/天猫。
- 拼多多。
- 后续其他线上店铺。

重点数据：

- 平台订单与退款。
- 商品和店铺映射。
- 活动、优惠和平台补贴。
- 流量、曝光、点击和转化。
- 广告投放及费用。
- 平台结算账单。

主要工作：

- 建立跨系统店铺、商品和 SKU 主数据映射。
- 建立平台订单、ERP 出库和售后的关联关系。
- 建立活动日历和活动对比模型。
- 上线活动策划、活动复盘和商品上新建议智能体。
- 让建议引用历史相似活动、商品表现、库存和企业经验。

验收标准：

- 可以解释平台下单与 ERP 出库之间的差异。
- 活动复盘能区分销售增长、优惠成本、广告成本、退款和库存消耗。
- 上新建议能列出使用的数据、相似案例、风险和假设。
- 对无法获得的平台字段明确标注，不用替代指标冒充。

阶段结束时，平台升级为“能够辅助经营决策的企业业务大脑”。

### 阶段 4：资金数据与业财融合

阶段目标：把业务发生、平台结算和银行到账串成一条链路。

推荐顺序：

1. 先用账单文件导入建立统一模型和核对方法。
2. 优先接企业支付宝或能力成熟的官方接口。
3. 再逐家接银行银企直联、开放银行或企业网银数据。

第一版只读：

- 账户余额。
- 收支流水。
- 对账单和回单索引。
- 平台结算和提现记录。

主要工作：

- 建立统一账户、流水和对手方模型。
- 建立账户级和角色级权限。
- 建立销售、退款、结算、提现、到账的核对模型。
- 上线现金流日报和到账差异分析智能体。
- 对敏感账号、对手方和备注实施脱敏。

验收标准：

- 余额和流水能与银行或支付平台账单核对。
- 可以发现未到账、重复到账、金额不一致和异常大额收支。
- 普通员工默认看不到银行明细。
- 所有资金查询均有审计记录。
- 平台不具备付款、转账、提现等资金操作能力。

阶段结束时，平台升级为“业财一体的经营分析大脑”。

### 阶段 5：管理驾驶舱与主动预警

阶段目标：从员工主动提问，升级为系统持续观察并主动提醒。

主要工作：

- 建立管理层经营驾驶舱。
- 建立日报、周报、月报模板。
- 建立异常检测规则和阈值。
- 建立销售下滑、退款上升、库存积压、缺货、现金异常等预警。
- 支持从图表继续追问原因。
- 支持从对话跳转到对应指标和明细证据。

验收标准：

- 驾驶舱与 AI 问数使用同一指标服务。
- 预警包含触发原因、影响范围、证据和建议责任人。
- 预警可以确认、忽略、分派和关闭。
- 能衡量误报率、漏报率和处理时效。

阶段结束时，平台升级为“主动感知企业状态的经营驾驶舱”。

### 阶段 6：决策、行动与反馈闭环

阶段目标：让企业大脑不仅提出建议，还能在受控范围内推动执行并学习结果。

第一批只做低风险、可撤销的动作：

- 创建待办和复盘任务。
- 生成活动方案草稿。
- 生成补货建议单，不直接下采购单。
- 生成日报、周报并提交人工确认。
- 将预警分派给责任人。

任何外部写入动作必须具备：

- 明确授权。
- 人工确认或审批。
- 操作范围和额度限制。
- 幂等机制。
- 完整审计。
- 失败回滚或补偿方案。

形成反馈闭环：

```text
AI 建议
→ 人是否采纳
→ 实际采取了什么动作
→ 结果如何
→ 与预测差异多大
→ 经验进入下一次分析
```

验收标准：

- 每项建议都可以追踪采纳状态和实际结果。
- 系统能够区分“AI 建议”“人工决定”和“系统执行”。
- 未经确认不执行高风险外部动作。
- 可以根据历史建议效果评估智能体，而不只看对话满意度。

阶段结束时，平台才真正形成企业大脑的基本闭环。

## 6. 各阶段依赖关系

```text
阶段 0 工程地基
  ↓
阶段 1 万里牛数据闭环
  ↓
阶段 2 可信问数
  ↓
阶段 3 平台经营决策 ──┐
  ↓                    │
阶段 4 业财融合         │
  └──────────────┬─────┘
                 ↓
阶段 5 驾驶舱与主动预警
                 ↓
阶段 6 行动与反馈闭环
```

知识库、记忆、权限、审计和数据质量不是后置阶段，而是从阶段 0 开始持续建设。

## 7. 第一阶段不要做什么

为了避免平台在数据还不可信时就堆叠功能，阶段 0～1 明确不做：

- 不让 AI 自由生成 SQL 查询生产数据库。
- 不在每次用户提问时临时全量调用万里牛。
- 不把所有原始 API 直接暴露给智能体。
- 不一次接完所有万里牛接口。
- 不在第一批接十几家银行。
- 不做银行付款、转账、提现。
- 不先做一套与指标服务分离的驾驶舱。
- 不用大模型回答来掩盖指标口径尚未确认的问题。

## 8. 近期执行清单

下一步建议按以下顺序进入实施：

1. 由业务负责人确认销售额、订单、退款、库存等核心口径。
2. 确认万里牛正式/沙箱应用、AppKey、Secret 和已授权接口。
3. 确定第一批同步历史范围和账套范围。
4. 建立独立经营数据库和迁移脚本。
5. 建立连接器、同步任务和指标工具的工程骨架。
6. 先打通店铺接口，验证签名、分页、权限和落表。
7. 再接仓库、商品、库存、销售出库和售后。
8. 连续核对至少 3 个营业日数据。
9. 上线三个只读指标工具。
10. 进入阶段 2，建设第一个经营分析智能体。

## 9. 项目成功指标

企业大脑不以“创建了多少智能体”或“接了多少接口”为主要成功指标。建议长期跟踪：

- 数据同步成功率和延迟。
- 核心指标与业务系统核对一致率。
- 指标口径覆盖率。
- 问数正确率和可解释率。
- 越权拦截和审计完整率。
- 预警有效率和处理时效。
- 建议采纳率。
- 建议采纳后的业务改善结果。
- 员工节省的分析时间。
- 管理决策从发现问题到采取行动的周期。

## 10. 最终形态

最终用户看到的不是七层技术架构，而是几个清晰入口：

- 员工问：“昨天销售怎么样？”系统先取数、再分析、再回答。
- 运营问：“这个活动能不能做？”系统参考历史数据、库存、产品和企业经验给出建议。
- 商品运营问：“这个新品怎么搭配上架？”系统寻找历史相似商品和组合表现。
- 管理层打开驾驶舱，看到公司经营、库存、现金流和异常预警。
- 系统发现异常后主动提醒责任人，并跟踪问题是否处理。
- 每次决策的依据、执行和结果都能沉淀，成为下一次决策的企业记忆。

这时，知识库不再是孤立的资料库，数据库也不只是报表来源，智能体更不是单独的聊天机器人；三者共同组成一个受控、可信、可反馈的企业智能系统。
